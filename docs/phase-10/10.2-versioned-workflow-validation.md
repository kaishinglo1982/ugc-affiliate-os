# Phase 10.2 — Versioned Workflow Definitions & Validation

## Status

Implementation foundation complete. Database migration remains a separate migration-governed follow-up within 10.2.

## Implemented

- strict Zod schema for versioned workflow definitions;
- stable workflow and step keys;
- semantic validation for duplicate keys and order values;
- unknown- and self-dependency rejection;
- cycle detection;
- mandatory approval-step resource configuration;
- mandatory condition expression configuration;
- typed semantic validation errors;
- immutable run-snapshot helper;
- unit tests for schema, graph rules, typed failures and snapshots.

## Existing models reused

The implementation extends the existing conceptual model around:

- `WorkflowDefinition`;
- `WorkflowStepDefinition`;
- `WorkflowRun`;
- `WorkflowStepRun`;
- shared `Approval` resources.

No parallel workflow or approval model is introduced.

## Migration-safe schema delta

The Data Platform work packet must extend the existing Prisma models instead of replacing them:

### WorkflowDefinition

- `key String`
- `version Int @default(1)`
- `definitionHash String?`
- composite uniqueness for workspace, key and version

### WorkflowRun

- `workflowVersion Int`
- `definitionSnapshot Json`
- `definitionHash String?`
- `correlationId String`
- `idempotencyKey String?`

The run snapshot is authoritative after execution begins. Later edits to a draft or a new workflow version must never alter historic runs.

## Activation policy

A workflow version may transition to `ACTIVE` only when:

1. Zod parsing succeeds;
2. semantic graph validation succeeds;
3. referenced agents and tools exist and are enabled;
4. policy and approval references resolve;
5. definition hash and immutable activation snapshot are persisted;
6. the previous active version is retained for historic runs and rollback.

## Required remaining evidence

- Prisma migration and generated client;
- persistence service for atomic version creation;
- activation transaction with optimistic concurrency;
- database integration tests;
- API input validation and RBAC tests;
- full repository gates: typecheck, lint, test and build.

## Rollback

The validation module is additive. Rollback removes its imports and files. A later database migration must use additive nullable/defaulted columns so application rollback remains possible without destructive schema reversal.
