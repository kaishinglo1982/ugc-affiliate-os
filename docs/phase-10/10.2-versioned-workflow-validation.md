# Phase 10.2 — Versioned Workflow Definitions & Validation

## Status

**Implementation complete.** Phase 10.2 is closed at code and migration level. Repository-wide CI evidence remains part of the Phase-10 completion gate and must be recorded when GitHub Actions exposes runs for the branch.

## Implemented

- strict Zod schema for versioned workflow definitions;
- stable workflow and step keys;
- semantic validation for duplicate keys and order values;
- unknown- and self-dependency rejection;
- cycle detection;
- mandatory approval-step resource configuration;
- mandatory condition expression configuration;
- typed semantic validation errors;
- immutable run-snapshot helper;
- SHA-256 definition hashes;
- additive migration for existing workflow tables;
- unique workflow versions per workspace and workflow key;
- immutable definition snapshots, correlation IDs and idempotency keys on runs;
- atomic workflow and step creation;
- transactional activation with row locking and expected-version check;
- prior active-version superseding without destructive updates;
- idempotent workflow-run creation;
- workspace-scoped reads and writes;
- unit tests and PostgreSQL integration tests.

## Existing models reused

The implementation extends the existing canonical models:

- `WorkflowDefinition`;
- `WorkflowStepDefinition`;
- `WorkflowRun`;
- `WorkflowStepRun`;
- shared `Approval` resources.

No parallel workflow or approval model was introduced.

## Persistence implementation

The persistence boundary is split into:

- `src/lib/workflows/validation.ts` — schema and semantic graph validation;
- `src/lib/workflows/repository.ts` — provider-independent service and contracts;
- `src/lib/workflows/postgres-adapter.ts` — PostgreSQL transaction adapter;
- `prisma/migrations/20260716233000_phase10_workflow_versioning/migration.sql` — additive migration.

The PostgreSQL adapter deliberately targets the migrated tables directly. This prevents generated-client drift from blocking the migration rollout and preserves compatibility while the main Prisma schema is reconciled in the normal schema-governance cycle.

## Activation policy

A workflow version transitions to `ACTIVE` only when:

1. Zod parsing succeeds;
2. semantic graph validation succeeds;
3. the exact workspace and expected version match;
4. the target row is locked for the activation transaction;
5. previous active versions with the same workflow key are paused and retained;
6. activation time and definition hash remain persisted;
7. historic workflow runs continue using their stored snapshots.

## Rollback

The database changes are additive. Application rollback can stop using the new columns while retaining historical data. The new unique indexes and columns should only be removed in a separately reviewed destructive migration after confirming that no workflow runs depend on stored version snapshots.
