## CI status

Investigated in depth this session. `.github/workflows/ci.yml` fails instantly (0 jobs dispatched) on every push, on `master` and on every feature branch, going back through the full visible run history — this predates Phase 10.1. The file passes GitHub Actions JSON-schema validation (`@action-validator/cli`, exit 0) and is byte-identical between the local working tree and what GitHub stores, ruling out a YAML/schema defect or a sync problem. `actions/permissions` reports `enabled: true, allowed_actions: "all"` and the workflow's `state` is `active`. The repository is private; the most probable remaining cause is an account-level Actions spending/minutes limit, which requires repository-owner access to GitHub Billing settings to confirm or fix — outside this session's credentials. Every prior Phase-10 completion report (10.1–10.5) listed this as an open checkbox without diagnosing it; this report documents the actual investigation so it is not re-investigated from scratch next time.

## Security

All approval and workflow-state mutations are scoped by `workspaceId`. The four-eyes check blocks self-approval unconditionally (no override path exists in this service). The single-use check blocks decision replay unconditionally.

## Technical debt discovered (out of scope for 10.6, flagged for visibility)

- `prisma/schema.prisma`'s `ApprovalResourceType` enum lists ~24 values; the live database (and, per `git grep`, every migration file) only defines 5 of them (`product`, `affiliate_offer`, `product_opportunity`, `product_campaign_candidate`, and this session's `agent_tool_invocation`). The other ~19 values were added to the Prisma schema without a corresponding `ALTER TYPE ... ADD VALUE` migration and would fail at runtime if used. This predates Phase 10 and was not introduced or fixed here.
- `src/app/api/approvals/[id]/decide/route.ts` has no single-use or four-eyes guard (see the design doc). Not fixed here to avoid widening this handoff's blast radius into a live, auth-guarded API route; flagged as 10.6's "Remaining acceptance work".

## Rollback

The migration only adds a nullable, unindexed-by-default-but-FK'd column (`approvalId`) to `WorkflowStepRun`. Application rollback is: stop calling `PostgresApprovalGateService`; the unused column is inert. Dropping it, if ever required, needs a separate reviewed migration.
