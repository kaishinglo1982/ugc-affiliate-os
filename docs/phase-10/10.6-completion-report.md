# Phase 10.6 — Human Approval Gates

**Branch:** `feat/carryos-core-bound-consolidation-20260916`  
**Status:** IMPLEMENTED — CI verification pending

## Delivered

- Existing `Approval` model extended instead of introducing a parallel approval request core.
- Durable `ApprovalDecision` history with unique approver constraint.
- Configurable 1–4 approvers.
- Four-eyes enforcement: requester cannot approve a multi-approver request.
- Expiry enforcement before a decision is accepted.
- Optional escalation timestamp plus durable `escalatedAt` marker.
- HMAC decision fingerprint using the server-side `AUTH_SECRET`; the raw secret is never persisted.
- Atomic decision transaction re-checks pending/unconsumed state to prevent replay races.
- Repeated decisions by the same approver are rejected.
- Rejected approvals become terminal immediately.
- Approved approvals become terminal only after the required number of distinct approvers has approved.
- Separate `consumeApproval` operation enforces single-use execution consumption.
- Requester identity is derived from the authenticated session; client-supplied `requestedBy` is no longer authoritative.
- Decision API uses the tenant-bound approval service.

## Security boundaries

- Workspace is resolved before persistence.
- Approval state is re-checked inside the transaction.
- Four-eyes is enforced server-side.
- Decision signatures are derived from server-only secret material.
- No approval token or secret is exposed in API payloads.
- No external side effect is executed by the decision endpoint.
