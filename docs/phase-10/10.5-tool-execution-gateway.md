# Phase 10.5 — Mandatory Tool Execution Gateway & Policy Enforcement

## Status

Complete. `PostgresToolExecutionGateway` is the single sanctioned path for invoking an `AgentToolDefinition`.

## Objective

Close the gap recorded in `10.1-existing-state-inventory.md`: "Tool policy enforcement | Policy data exists | No single mandatory execution gateway proven | 10.5". `AgentToolDefinition`, `AgentToolPolicy` and `AgentToolCall` already carried every column the gateway needed; no new tables were introduced.

## Delivered

- `PostgresToolExecutionGateway.execute()` as the only sanctioned call path for a tool;
- per-(workspace, tool) atomic policy evaluation and rate-limit accounting via `pg_advisory_xact_lock`, so concurrent callers cannot race past `rateLimitPerMin`;
- most-restrictive-wins aggregation across multiple `AgentToolPolicy` rows for the same tool (any denying policy denies);
- enforcement of `enabled`, `allowedAgentKeys`, `maxCostPerCall` (against a caller-declared `estimatedCost`), `rateLimitPerMin`, and `requiresApproval`;
- every outcome — `SUCCESS`, `DENIED`, `FAILED` — is recorded as an `AgentToolCall` audit row, including the denial reason;
- a typed `ToolExecutionDeniedError` with a machine-readable `reason` for callers and workflow-step-run error handling;
- unit-free integration test suite covering all seven decision paths plus concurrent rate-limit enforcement.

## Approval integration

`AgentToolPolicy.requiresApproval` gates execution against the shared `Approval` model rather than a second approval table. The gateway does not create or manage approval lifecycle (queues, expiry, escalation) — that orchestration is explicitly Phase 10.6's scope per the gap matrix. 10.5 only checks for an existing `Approval` row with:

- `resourceType = 'agent_tool_invocation'` (new enum value, added because no existing `ApprovalResourceType` fit a tool invocation — the 10.1 inventory explicitly permits extending the enum "only where necessary");
- `resourceId = <toolId>`;
- `status = 'APPROVED'`;
- not expired.

No approval, or an approval that is pending/rejected/expired, is a denial (fail closed).

## Atomicity design

Denials must still be committed as an audit row, so `reserveOrDeny` never throws from inside its own transaction — a thrown error there would roll back the very `AgentToolCall` insert meant to record the denial. Instead the transaction always resolves with an `{ ok: true | false }` outcome and commits; the caller throws only after the commit succeeds. The one exception is `TOOL_NOT_FOUND`, which has no valid `toolId` to attach an audit row to — rolling back that no-op transaction is harmless because nothing was written.

The actual tool `executor` runs **outside** the transaction and outside the advisory lock, so slow or side-effecting tool calls never hold a workspace/tool-scoped lock.

## Reuse decision

The gateway is an enforcement layer over the existing `AgentToolDefinition` / `AgentToolPolicy` / `AgentToolCall` foundation. It introduces no second tool-governance schema and no second approval table. Budget-policy/cost-reservation enforcement (`BudgetPolicy`, `CostReservation`) remains out of scope — that is Phase 10.7.

## Security rules

- Every query is scoped by `workspaceId`; a call for one workspace can never read or consume another workspace's tool, policy, call history, or approval.
- Deny by default: unknown tool, disabled tool, missing allow-list membership, missing/expired approval, or exceeded cost/rate limits all deny before the executor runs.
- No cross-tenant approval can satisfy a tool-invocation approval check because the lookup is scoped by `workspaceId` and `resourceId = toolId`.
