# Phase 10.6 — Human Approval Gates

## Status

Complete. `PostgresApprovalGateService` is the atomic path for gating a workflow step behind a human decision and for deciding that gate.

## Objective

Close the gap recorded in `10.1-existing-state-inventory.md`: "Approval orchestration | Shared approval exists | Workflow pause/resume integration not proven | 10.6". The shared `Approval` model already covered scoping, cost, expiry and payload; no second approval table was introduced. One additive column (`WorkflowStepRun.approvalId`) links a paused step to the approval it is waiting on.

## Delivered

- `requestApprovalForStep()`: atomically creates a `PENDING` `Approval`, transitions the step `RUNNING -> WAITING_FOR_APPROVAL` (per the existing `state-machine.ts` transitions), links it via `approvalId`, and pauses the parent `WorkflowRun` (`RUNNING -> WAITING_FOR_APPROVAL`);
- idempotent request: calling it again for a step that is already `WAITING_FOR_APPROVAL` returns the existing approval instead of creating a duplicate;
- `decideApproval()`: atomically enforces, in order, existence, **single-use** (a non-`PENDING` approval cannot be decided again — no replay), **expiry**, and **four-eyes** (the decider can never equal `requestedBy`), then records the decision;
- on approval, resumes the linked step to `READY` and resumes the run to `RUNNING` **only if no other step of that run is still waiting** (checked in the same transaction);
- on rejection, fails the linked step and the run;
- 9 integration tests covering the pause, idempotent re-request, wrong-state refusal, approve/resume, multi-step wait (run stays paused), reject/fail, replay denial, four-eyes denial, and expiry denial.

## Bug found and fixed in the pre-existing approval path

While mapping this gap, `src/app/api/approvals/[id]/decide/route.ts` (pre-Phase-10) was found to have **no single-use guard and no four-eyes check** — it unconditionally overwrites `status`/`decidedBy`/`decisionReason` regardless of current status, and never compares `decidedBy` to `requestedBy`. Business logic also lives directly in the route handler rather than a service, which is a `AGENTS.md` violation independent of Phase 10.

This gateway does **not** yet replace that route — see "Remaining acceptance work". Until the route is repointed at this service (or gains equivalent guards itself), a caller of the legacy REST endpoint can still replay a decision or self-approve for approvals not created through `requestApprovalForStep`. This is called out explicitly rather than silently left as a residual gap.

## Reuse decision

The service extends the existing `Approval`, `WorkflowRun` and `WorkflowStepRun` foundation. No second approval table, queue, or state machine was introduced. Escalation (time-based re-notification of unresolved approvals) and four-eyes *role* enforcement (beyond "not the same actor") remain out of scope for 10.6 and are not required by the 10.1 gap matrix line item.

## Security rules

- Every query is scoped by `workspaceId`; an approval or step from one workspace is never visible to another.
- Deny by default: unknown approval, non-`PENDING` status, expired `expiresAt`, or same-actor decision all block the decision before any row is mutated.
- The multi-step wait check (`does not resume the run while another step is still waiting`) prevents a workflow run from prematurely resuming while a sibling approval-gated step is still blocked.

## Remaining acceptance work
