# Phase 10.2 — Versioned Workflow Definitions & Validation

Status: **implementation packet / design contract**
Branch: `feat/phase-10-2-workflow-validation`
Baseline: `master`

## Goal

Make workflow definitions safe to execute before changing worker orchestration. Reuse the existing `WorkflowDefinition`, `WorkflowStepDefinition`, `WorkflowRun`, and `WorkflowStepRun` models. Do not create parallel workflow tables.

## Current evidence

The Phase 10.1 inventory identifies existing workflow persistence and identifies these gaps:
- no proven immutable definition snapshot attached to a run;
- no proven central strict Zod compiler/validator;
- workflow graph validation is not yet evidenced;
- existing JSON configuration must remain backward-compatible while being validated.

This document is a scoped work contract, not evidence that runtime validation has already shipped.

## Required implementation

1. Read `AGENTS.md`, `.agents/coordinator.md`, `.agents/data-platform.md`, `.agents/app-runtime.md`, and local Next.js documentation before code edits.
2. Inspect the exact current Prisma models, migrations, generated client conventions, workflow services, route handlers, and tests.
3. Define strict Zod schemas for workflow definitions, step definitions, and each supported step type (`AGENT`, `TOOL`, `APPROVAL`, `CONDITION`). Reject unknown keys where safe; retain explicit compatibility handling for existing persisted rows.
4. Validate graph structure before saving or activating a definition:
   - unique, non-empty step keys;
   - all referenced next-step keys exist;
   - valid entry point;
   - no invalid terminal transitions;
   - bounded graph size and JSON payload size;
   - condition branches are explicit;
   - no unrecognized step type or action;
   - required configuration exists for the chosen step type.
5. Pin a canonical definition version or immutable JSON snapshot on each run. A run must execute the exact validated definition it started with, even if the editable definition changes later.
6. Validate on create/update/activate and again immediately before execution. Return stable, non-secret error codes and field paths.
7. Add tests for valid definitions, malformed config, unknown keys/types, missing step references, duplicate keys, invalid branch targets, definition updates after run creation, legacy rows, and workspace isolation.
8. Add migration only if the inspected schema truly lacks the required snapshot/version fields. Never rewrite an applied migration; use a new forward migration and document rollback implications.

## Security invariants

- Workspace identity comes from trusted server context, never caller-controlled JSON.
- Every definition/run/step lookup and mutation is workspace-scoped.
- Invalid or unvalidated definitions fail closed.
- Workflow content and tool outputs are untrusted input; they cannot override tool policy.
- This phase must not introduce direct tool execution or bypass the canonical governance gateway.
- No secrets or raw credentials in workflow JSON, validation errors, or logs.

## Acceptance gates

- [ ] Existing schema and migrations inventoried before editing.
- [ ] A single canonical validator is used by all write/activation paths.
- [ ] Each new run is pinned to the exact validated definition version/snapshot.
- [ ] Existing valid workflows remain loadable; invalid legacy workflows are blocked with actionable errors.
- [ ] Negative cross-workspace tests pass.
- [ ] Typecheck, lint, unit/integration tests, migration replay, and build pass.
- [ ] Exact-head CI evidence recorded; no production deployment until the repository's global release gate is green.
