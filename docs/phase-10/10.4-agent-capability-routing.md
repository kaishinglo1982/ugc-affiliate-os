# Phase 10.4 — Agent Capability Registry & Deterministic Task Routing

## Status

Core routing implementation complete. Durable registry persistence and runtime task-assignment integration remain the final 10.4 work packet.

## Delivered

- strict Zod contracts for agents, capabilities, health and routing strategies;
- workspace-scoped capability registry;
- capability-version matching;
- required-tool and required-provider enforcement;
- health, enabled-state and concurrency-capacity filtering;
- deterministic stable tie-breaking;
- routing strategies for least load, lowest cost, fastest latency and highest success rate;
- deny-by-default when no eligible agent exists;
- unit tests for determinism, workspace isolation, availability, compatibility and strategy selection.

## Deterministic ordering

The default strategy sorts candidates by:

1. descending explicit priority;
2. ascending stable agent key;
3. descending agent version.

Identical registry state and identical request therefore produce the same routing decision.

## Security rules

- Agents from another workspace are never considered.
- Offline, maintenance, degraded, disabled or saturated agents are rejected.
- Missing capability, insufficient capability version, missing tools or missing provider compatibility results in denial.
- Unknown routing situations never fall back to an arbitrary agent.

## Reuse decision

The registry is an orchestration service over the existing agent, tool-policy and workflow foundations. It does not introduce a second workflow runtime or bypass `AgentToolPolicy`. Tool authorization remains a separate mandatory enforcement step in Phase 10.5.
